## 1. PROJECT OVERVIEW

**Project name:** ResearchPilot AI

**Goal:** An AI-powered research assistant where a user uploads research papers (PDFs) and can chat with them, compare them, and — in later phases — get literature reviews, gap analysis, citation generation, and a knowledge graph. Positioned as "your own NotebookLM + Perplexity + Semantic Scholar."

**Target users:** Primarily the builder's own use case first (a researcher reading papers, e.g. for IIT Patna research work), designed to generalize to any researcher/student who needs to read, question, and synthesize across many papers.

**Long-term vision (from the original idea notebook):** A 12-phase, resume-driven build where every phase ends in a deployed, working application:
- Chat with a single paper (Phase 1)
- Multiple papers, semantic search, collections (Phase 2)
- Notes, highlights, tags, GROBID metadata extraction (Phase 3)
- Multi-paper comparison (Phase 4)
- Literature review generation with export (Phase 5)
- Research gap detection (Phase 6)
- Interactive knowledge graph (Phase 7)
- Figure/equation explanation (Phase 8)
- Similar-paper recommendations (Phase 9)
- Research dashboard/analytics (Phase 10)
- Collaboration (share collections, comments) (Phase 11)
- Production polish: monitoring, rate limiting, email verification, forgot password, mobile-responsive UI (Phase 12)

Other features mentioned in the original brainstorm but not yet scheduled into a specific phase: citation generator (APA/IEEE/ACM/BibTeX), AI mind maps, research timeline visualization, OCR for scanned PDFs, DOCX/TXT upload support (Phase 1 is PDF-only).

**Resume impact (explicit motivation, stated in the original planning notebook):** The project is deliberately built and deployed incrementally so that the GitHub history itself demonstrates engineering discipline — each phase is a "resume line" that gets stronger over time (e.g. "Month 1: built citation-aware RAG chat" → "Month 2: added multi-document reasoning and literature review generation" → "Month 3: knowledge graph and research-gap detection"). The stated skill set this is meant to demonstrate to recruiters: Backend, Frontend, AI/RAG, LLMs, Embeddings, Vector DB, Postgres, Docker, Auth, Cloud deployment, REST APIs, CI/CD, System Design.

**Current development phase:** **Phase 1 ("Single-document upload + chat, deployed")**, in progress. Within Phase 1: authentication is complete (signup + login, backend and frontend), and the first protected-route dependency (`get_current_user`) is now implemented and tested (Task 3A) — not yet consumed by any route. Document upload/processing/chat — the core RAG loop — is **not started yet** (Task 3B, next up, plan already approved). Nothing has been deployed yet (no live Railway/Vercel URLs exist yet).

## 2. PRODUCT DESCRIPTION

### What the product does (end state of Phase 1)
A user signs up with email + username + password, logs in, uploads a single PDF at a time, and can chat with that document. Answers are grounded in the paper's actual content via retrieval-augmented generation (RAG) and cite which page/chunk they came from. Chat history persists per document.

### Full Phase 1 user flow (target — not all built yet)
```
Visitor
  │
  ▼
Sign up (email + username + password) ──► auto-login ──► Dashboard (empty state)
  │
  ▼
Click "Upload Paper" ──► select PDF ──► upload starts
  │
  ▼
Dashboard shows document card: status = "Processing..."
  │  (polling every 3s)
  ▼
Status flips to "Ready"
  │
  ▼
Click document ──► Document page opens
  │
  ▼
Left: PDF preview (basic viewer, no highlighting yet)
Right: Chat panel
  │
  ▼
Type question ──► answer returned ──► shows "Source: page 4" under answer
  │
  ▼
Refresh page ──► chat history persists
  │
  ▼
Log out and back in ──► document and chat history still there
```

### End-to-end system flow for upload → chat (design target, Section 5 of the Phase 1 design doc — **not implemented yet**)
```
1. Frontend: POST /api/v1/documents/upload (multipart file)
2. Backend: save file to storage, insert `documents` row (status=uploading),
   enqueue background job, return document_id immediately (202 Accepted)
3. Frontend: redirects to dashboard, polls GET /documents/{id}/status
4. Worker (Arq):
     a. status -> processing
     b. extract text (PyMuPDF)
     c. chunk text (~500 tokens, 50 token overlap)
     d. call embedding API per chunk (batched)
     e. insert document_chunks rows (content + embedding vector)
     f. status -> ready  (or -> failed with error logged)
5. Frontend: status becomes "ready", user opens document page
6. User sends chat message:
     POST /api/v1/documents/{id}/chat/sessions/{session_id}/messages { content }
7. Backend:
     a. embed the user's question
     b. pgvector similarity search over this document's chunks (top-k=5)
     c. build prompt: system instructions + retrieved chunks + question
     d. call LLM API
     e. save both user message and assistant message (+ source_chunk_ids)
     f. return answer (full response for Phase 1; streaming is a stretch goal, not a requirement)
8. Frontend renders answer + "Source: page N" line(s) under it
```

### Features implemented so far
1. **Email/username/password signup** — backend endpoint + frontend form, fully working and tested.
2. **Login (JWT access token issuance)** — backend endpoint + frontend form, fully working and tested.

## 3. CURRENT ARCHITECTURE

### Backend
**FastAPI (Python, async).** Chosen over Django REST Framework (too batteries-included/ORM-first for this MVP) and Node/Express (would split the stack across two languages when Python is already doing the ML/RAG work). FastAPI gives native async, Pydantic-based request/response validation that doubles as data contracts, and auto-generated OpenAPI docs at `/docs`. It's also the de-facto standard for Python AI/RAG backends, so more reference code exists for the retrieval pipeline work ahead.

### Frontend
**React + TypeScript + Vite.** Chosen over Next.js (its SSR/routing conventions aren't needed for an authenticated dashboard app — SEO doesn't matter here) and Vue (smaller ecosystem for the chat/streaming UI kit needs). TypeScript catches API contract mismatches at compile time; Vite gives fast dev builds. Routing/state are owned directly (React Router + Context, no Redux/Zustand) rather than prescribed by a framework — deliberately avoiding a state library "before you feel the pain of not having one."

### Database
**PostgreSQL**, chosen for relational integrity across users/documents/chats, JSONB for future flexible metadata, and — critically — a mature vector extension.

**Vector store: `pgvector` (a Postgres extension), not a separate Qdrant service, for Phase 1.** This was an explicit pushback against the original idea notebook's "Postgres + Qdrant + Redis from day one" plan. Rationale: embeddings live in the *same* database as metadata, so Phase 1 has one database to run/back up/migrate instead of two. pgvector supports HNSW/IVFFlat indexing and comfortably handles hundreds of thousands of chunks — far beyond one user's paper collection. Because the schema keeps embeddings in their own table (`document_chunks`), **migrating to Qdrant later is a swap of one retrieval service, not a rewrite.** Qdrant is explicitly flagged as the Phase-4+ upgrade once multi-paper/multi-user scale justifies the operational cost.

### Authentication
**JWT (currently access-token only in the actual implementation)**, using **PyJWT** directly (not `python-jose`) and **`bcrypt`** directly (not `passlib`) — see Section 15 for why the implementation diverged from the Phase 0 doc's suggested libraries. Google OAuth via Authlib was planned but not started; deferred to Phase 2/12.
- Stateless, scales horizontally, no server-side session storage needed.
- Tradeoff accepted: the team owns token refresh/revocation logic themselves.
- `get_current_user` (Task 3A) verifies the bearer token via `HTTPBearer`, not `OAuth2PasswordBearer` — chosen because `/auth/login` accepts a JSON body, not the OAuth2 password-flow's form-encoded contract; `OAuth2PasswordBearer` would misrepresent that in the generated Swagger docs.

### AI pipeline
**Not built yet.** Planned design (from the Phase 1 design doc):
- **PDF text extraction:** PyMuPDF (`fitz`) — fast, dependency-light, sufficient for chunking/chat. GROBID (structured title/authors/references extraction, the tool Semantic Scholar itself uses) is explicitly deferred to Phase 3 because it's a separate Java service.
- **Chunking:** ~500 tokens per chunk, 50-token overlap.
- **Embeddings:** called via an external embedding API (provider not yet locked in — Anthropic or OpenAI per the env var scaffolding), stored in the `document_chunks.embedding` pgvector column (`vector(1536)`, i.e. sized for OpenAI's `text-embedding-3-small`/`ada-002` dimensionality).
- **Retrieval:** pgvector cosine/L2 similarity search, top-k=5, scoped to the one document being chatted with.
- **LLM orchestration:** hand-rolled — **direct API calls + a custom `rag_service.py`, deliberately not LangChain.** Rationale: for a project meant to demonstrate RAG engineering skill, hand-rolling chunk→embed→retrieve→prompt-assemble is more valuable in interviews than hiding it behind LangChain's abstractions, and avoids LangChain's version churn/debugging pain. LlamaIndex is flagged as worth reconsidering once Phase 5 (literature review generation) needs multi-document synthesis primitives.
- **LLM provider:** Claude or OpenAI, switchable via `LLM_PROVIDER` env var (planned, not yet in `config.py`).

### Storage
**Local disk for Phase 1** (`STORAGE_PATH`/`UPLOAD_DIR`, planned env var), with a storage abstraction so swapping to S3-compatible storage later doesn't touch calling code. Not implemented yet — no `documents` table, no upload endpoint, no storage service exist in the repo yet. **Task 3B's approved plan uses UUID-based on-disk filenames (never the user's original filename) to avoid path-traversal risk, and treats local-disk durability across deploys as an accepted Phase-1 trade-off** (see Task 3 planning discussion) — a Railway persistent volume is a deployment-time follow-up, not a code change.

### Deployment (planned, nothing live yet)
```
Frontend  →  Vercel (auto-deploy from `main`)
Backend   →  Railway (Docker deploy, auto-deploy from `main`)
Worker    →  Railway (second service, SAME image as backend, different start command)
Postgres  →  Railway managed Postgres (pgvector extension enabled)
Redis     →  Railway managed Redis
```
Everything on Railway (except the frontend on Vercel) to minimize the number of dashboards a solo dev juggles in Phase 1. Vercel is worth the split for its free tier/CDN and for decoupling frontend deploys from backend deploys. **CI/CD:** GitHub Actions — lint + test on every PR (now actually running `pytest` against a real Postgres service container, fixed in Task 2.2 — see Section 15), deploy on merge to `main` (the deploy-on-merge step is still not wired up).

### Future microservices
- **Arq worker** (background jobs: PDF parsing, chunking, embedding) — same Docker image as the API, different start command. Introduced in the document-processing task, not before.
- **GROBID** — Java container, Phase 3, for structured citation/author/reference metadata.
- **Qdrant** — separate vector service, Phase 4+, only once multi-user scale makes pgvector's ceiling a real constraint.
- **Sentry** — error tracking, planned from "Phase 1" per the Phase 0 doc but not yet integrated in code.

### Purpose of every major folder
- **`backend/app/api/`** — HTTP routing layer only. Validates via Pydantic schemas (FastAPI does this automatically before the handler body runs), calls into `services/`, translates service-layer exceptions into HTTP status codes. **No business logic and no direct DB access belongs here.**
- **`backend/app/core/`** — cross-cutting concerns: configuration (`config.py`), security primitives (`security.py`), and now FastAPI dependencies (`deps.py`, added Task 3A). Nothing outside `core/` should touch `bcrypt`/`jwt`/`os.environ` directly.
- **`backend/app/db/`** — the async SQLAlchemy engine, session factory, declarative `Base`, and the `get_db()` FastAPI dependency. This is infrastructure, not models.
- **`backend/app/models/`** — SQLAlchemy ORM model definitions only (table shape). `__init__.py` here is the single required import point for Alembic autogenerate to see a model — this is enforced by convention, not by tooling, so it must be remembered when adding new models.
- **`backend/app/schemas/`** — Pydantic request/response contracts. Validation (e.g. password length, byte-limits) lives at this boundary so invalid requests are rejected before any service code runs.
- **`backend/app/services/`** — business logic. Routers call these; these never know about HTTP (no `Request`, no `HTTPException` inside a service — services raise their own domain exceptions that routers translate).
- **`backend/app/workers/`** — background job definitions (Arq tasks). Currently empty; will hold `process_document`/`generate_embeddings`-style tasks.
- **`backend/alembic/`** — migration environment + generated migration scripts.
- **`backend/tests/`** — pytest suite, run against a real Postgres test database (not mocked), full schema created/dropped per test via `Base.metadata.create_all`/`drop_all` rather than by running actual Alembic migrations (a deliberate speed-over-fidelity tradeoff, flagged as a known risk in the CHANGELOG).
- **`frontend/src/pages/`** — top-level routed views.
- **`frontend/src/components/`** — reusable UI pieces (folder exists, currently empty — no components have been extracted out of pages yet).
- **`frontend/src/context/` + `frontend/src/hooks/`** — deliberately split: the context module defines *what* the auth state is and *how* it's provided; the hook module defines *how it's consumed*. This split was a specific review-feedback decision (see `CHANGELOG.md` Task 2.3), intended to make each side easier to test in isolation later.
- **`frontend/src/services/`** — the only layer allowed to call `fetch`. Pages and context never call `fetch` directly.
- **`frontend/src/types/`** — TypeScript interfaces mirroring the backend's Pydantic schemas, kept in sync **by hand** (no shared codegen at this project's current scale — noted explicitly in the code as a scale-triggered thing to revisit).
- **`docs/`** — the three living docs (`ARCHITECTURE.md`, `API.md`, `ROADMAP.md`), meant to be updated every phase (in practice, `ROADMAP.md`'s task log has fallen behind — see Section 15).

Every later phase is meant to add files inside this existing structure (new `services/`, new `api/` routers, new frontend `pages/`) — **no reorganization is expected or wanted.**

## 6. DATABASE DESIGN

### Currently in the database (one table exists, one migration applied)

#### `users`
| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | primary key, default `uuid4()` (app-generated, not DB `gen_random_uuid()`) |
| `email` | VARCHAR(255) | unique, indexed, not null |
| `username` | VARCHAR(50) | unique, indexed, not null |
| `hashed_password` | VARCHAR(255) | not null |
| `is_active` | BOOLEAN | default `true`, not null |

## 8. AUTHENTICATION FLOW

**Current state: access-token-only JWT. No refresh token exists in the implementation despite being mentioned in the Phase 1 design doc's API sketch (see Section 15).**

### Signup
1. Frontend `SignupPage` collects email, username, password → calls `useAuth().signup()`.
2. `AuthContext.signup()` calls `authService.signup()` → `POST /api/v1/auth/signup` with `{ email, username, password }`.
3. Backend validates via `SignupRequest` (Pydantic): email format (`EmailStr`), username 3–50 chars, password 8–72 chars **and** ≤72 UTF-8 bytes (custom validator).
4. `auth.py` router calls `auth_service.create_user()`:
   - Checks email uniqueness → raises `EmailAlreadyExistsError` → router returns `409` "Email already registered".
   - Checks username uniqueness → raises `UsernameAlreadyExistsError` → router returns `409` "Username already taken".
   - Hashes the password with `bcrypt.hashpw` (via `security.hash_password`, which itself raises `PasswordTooLongError` if the byte length check is somehow bypassed — defense in depth over the schema validator).
   - Inserts the `User` row, commits, refreshes, returns the ORM object.
5. Router returns `UserPublic` (id, email, username, is_active, created_at — **never** the hash) with `201 Created`.
6. Frontend: `AuthContext.signup()` immediately calls `login()` with the same credentials (backend doesn't issue a token on signup) to land the user in an authenticated state.

### Login
1. `LoginPage` collects email + password → `useAuth().login()` → `authService.login()` → `POST /api/v1/auth/login` with `{ email, password }`.
2. Backend validates via `LoginRequest`, calls `auth_service.authenticate_user()`:
   - Looks up user by email.
   - If no user found: still runs `verify_password()` against a precomputed dummy hash (constant-time-ish defense against email-enumeration-via-timing), then raises `InvalidCredentialsError`.
   - If user found but password wrong: raises `InvalidCredentialsError`.
   - If user found, password correct, but `is_active` is `False`: raises `InvalidCredentialsError`.
   - **All three failure cases return the identical error** — this is deliberate, documented, and tested.
3. On success, router calls `create_access_token(subject=user.id)` and returns `TokenResponse{ access_token, token_type: "bearer" }` with `200`.
4. Frontend stores `access_token` and the submitted `email` in `localStorage` under `researchpilot_access_token` / `researchpilot_user_email`, updates React state, and the app treats `token !== null` as `isAuthenticated`.

### Protected routes
**The dependency exists now; no route consumes it yet.** `app/core/deps.py`'s `get_current_user` (Task 3A) verifies a bearer token and loads the `User`, fully unit-tested — but no endpoint currently checks the `Authorization` header, since no route declares `Depends(get_current_user)` yet. `docs/API.md` still correctly states "No endpoints are protected by this token yet." **Task 3B (document endpoints, plan already approved) is the first real consumer** — its checkpointed structure wires `get_current_user` into every document route.

### Token verification (mechanism, now wired into a dependency)
`app/core/security.py` has `decode_access_token(token) -> dict`, which calls `jwt.decode(token, settings.jwt_secret_key, algorithms=[settings.jwt_algorithm])` and raises `jwt.PyJWTError` (or a subclass like `ExpiredSignatureError`) on anything invalid/tampered/expired. **As of Task 3A, this function is called from `app/core/deps.py`'s `get_current_user`** — which extracts the `Authorization: Bearer <token>` header via `HTTPBearer`, calls `decode_access_token`, catches `jwt.PyJWTError`/`KeyError`/`ValueError` → `401`, looks up the user by the `sub` claim, 401s if not found or inactive, and returns the `User`. Not yet consumed by any route.

### Password hashing
`bcrypt` (direct library — `bcrypt.hashpw`/`bcrypt.checkpw`), not `passlib`. 72-byte input limit enforced explicitly (not left to bcrypt's silent truncation) because silent truncation would let two different long passwords hash identically.

### Dependencies involved
`pyjwt`, `bcrypt`, `email-validator` (runtime dependency of Pydantic's `EmailStr`, added ad hoc during Task 2.2 — wasn't in the original plan). `get_current_user` (Task 3A) introduces no new dependency.

## 10. CODING CONVENTIONS

**Naming:** `snake_case` for Python (files, functions, variables), `PascalCase` for Python classes and Pydantic/SQLAlchemy models, `camelCase` for TypeScript variables/functions, `PascalCase` for React components and TS types/interfaces. Route paths are centralized as constants (`frontend/src/constants/routes.ts`) rather than inlined as string literals.

**Folder organization:** Strict layering by responsibility, not by feature — `api/` / `core/` / `db/` / `models/` / `schemas/` / `services/` / `workers/` on the backend; `pages/` / `components/` / `context/` / `hooks/` / `services/` / `types/` / `constants/` on the frontend. New features add files *inside* this structure; the structure itself is the "permanent skeleton" and is not expected to be reorganized in later phases.

**Dependency injection:** FastAPI's `Depends()` is the only DI mechanism used — `get_db` for DB sessions, and `get_current_user` (built in Task 3A, not yet consumed by any route) for auth. Settings are accessed via the cached `get_settings()`/module-level `settings`, not re-read from `os.environ`.

**Error handling:**
- Services raise **domain-specific exceptions** (e.g. `EmailAlreadyExistsError`, `InvalidCredentialsError`) — plain `Exception` subclasses, no HTTP knowledge inside them.
- Routers catch those specific exceptions and translate them to `HTTPException` with the appropriate status code and a human-readable `detail`.
- The health endpoint deliberately catches broad `Exception` (with a `# noqa: BLE001` comment explaining why) because *any* DB failure should be treated as unhealthy.
- `get_current_user` (Task 3A) returns a uniform `401` for every failure case — same "don't leak which part failed" pattern as `auth_service`.
- Frontend: `services/api.ts` centralizes FastAPI error-body parsing (`{detail: string}` vs `{detail: [{msg}]}`) into one `extractErrorMessage()` function, so every caller gets a single readable string via a thrown `Error`.

**Validation:** Happens at the Pydantic schema boundary (`app/schemas/`), before any service code runs — e.g. password length and the bcrypt-byte-limit check are schema-level `Field` constraints and a `field_validator`, not service-level `if` statements.

**Response format:** JSON throughout. Success responses are typed Pydantic models (`response_model=...` on every route). Error responses always have a `detail` key — either a string (`HTTPException(detail="...")`) or a structured object (health check's 503 body), matching FastAPI's native shape so the frontend's single error-extraction function keeps working without route-specific special-casing.

**Architecture principles (explicitly stated in the docstrings of the code itself, not just the design docs):**
- Routers never touch the DB directly — always `api/` → `services/` → `models/`.
- Nothing outside `app/core/security.py` touches `bcrypt` or `jwt` directly.
- Nothing outside `app/core/config.py` reads `os.environ` directly.
- Every new SQLAlchemy model must be imported in `app/models/__init__.py` — this is the one place Alembic autogenerate (and anything else needing the full schema) looks.
- Frontend: nothing outside `services/*.ts` calls `fetch` directly.
- No state library (Redux/Zustand) until the pain of Context + local state is actually felt.
- No LangChain/LlamaIndex in Phase 1's RAG pipeline — hand-rolled, for the explicit purpose of being able to explain every step in an interview.

## 11. IMPORTANT DESIGN DECISIONS

*(Why things are the way they are, with rejected alternatives — pulled from the Phase 0 planning doc, the Phase 1 design doc, and decisions made and documented during actual implementation.)*

1. **FastAPI over Django REST Framework or Node/Express.** Django was rejected as too batteries-included/ORM-first when an admin panel isn't needed at MVP stage. Node/Express was rejected because it would split the stack across two languages when Python is already doing the ML/RAG work.

2. **pgvector over Qdrant for Phase 1**, explicitly pushing back on the original idea notebook's plan to use Qdrant from day one. One database instead of two to run/back up/migrate. Qdrant is deliberately deferred to "the phase where it earns its keep" (Phase 4+, multi-paper/multi-user scale). The schema is kept clean specifically so this later migration is "a swap of one retrieval service, not a rewrite."

3. **No LangChain/LlamaIndex for RAG orchestration.** Hand-rolling the retrieval pipeline is judged more valuable than abstracting it away, both to avoid LangChain's documented version-churn/debugging pain and — importantly — because the project's purpose includes demonstrating RAG engineering skill in interviews. LlamaIndex is flagged as worth reconsidering specifically for Phase 5 (literature review generation needs multi-document synthesis primitives it's good at).

4. **Arq preferred over Celery** for the background worker, given FastAPI's async-first architecture — Celery is the explicitly-noted fallback if richer scheduling/retry ecosystem is needed later.

5. **PyMuPDF over `unstructured` or GROBID for Phase 1 PDF parsing.** `unstructured` is heavier/slower and handles messier documents than needed yet. GROBID is "the actual industry tool" (used by Semantic Scholar itself) for structured author/reference/section extraction, but it's a separate Java service — real added operational complexity — so it's deliberately deferred to Phase 3 when citation-generation features actually need it.

6. **JWT over session cookies.** Stateless, scales horizontally without server-side session storage, and doesn't couple auth to server state if a mobile client is ever added. Tradeoff accepted: the team owns refresh/revocation logic.

7. **`bcrypt` direct + `PyJWT` direct, instead of the Phase 0 doc's suggested `fastapi-users`/`python-jose`+`passlib`.** This is a deviation from the original plan that happened during actual implementation (see Section 15) — smaller, more auditable surface area, fewer abstraction layers to understand and explain.

8. **JWT stored in `localStorage`, not an httpOnly cookie**, on the frontend. Documented, accepted tradeoff: httpOnly cookies would need backend changes that were out of scope for what was a frontend-only task at the time. This is real XSS exposure and is a candidate to revisit before Phase 1 is considered "production-ready" (see Section 15/19).

9. **Signup does not return a token; frontend auto-logs-in after signup** by calling the login endpoint with the same credentials, rather than adding a second code path on the backend that issues tokens from signup. Keeps the backend's token-issuance logic in exactly one place.

10. **The `/` route placeholder is inline in `App.tsx`, not a separate `HomePage.tsx` component.** Specific review-feedback decision to avoid creating a throwaway component that would just be deleted once the real dashboard is built.

11. **Docker Compose is local-dev only; Redis and the worker service are added only when the task that needs them arrives** (explicitly commented in `docker-compose.yml` itself) — not spun up speculatively ahead of need.

12. **Everything on Railway except the frontend (which goes to Vercel)**, to minimize the number of separate dashboards/configs a solo developer has to juggle during Phase 1, while still getting Vercel's free CDN tier and deploy-decoupling for the frontend.

13. **Streaming LLM responses is explicitly a nice-to-have for Phase 1, not a requirement** — return the full answer in one response first; only add streaming if time remains. Don't let it block deployment (Phase 1 design doc §5, and again in the Day-4 cut list, §20).

14. **Test isolation via a function-scoped DB engine fixture, not a module-scoped one** — because `asyncpg` connections are bound to the event loop they were opened in, and `pytest-asyncio` gives each test function its own loop by default. This was a real bug (see Section 15) fixed by this specific fixture-scoping decision.

15. **Tests create schema via `Base.metadata.create_all()`/`drop_all()`, not by running actual Alembic migrations**, for speed — at the accepted cost of the test suite never actually exercising the migration files themselves. Flagged explicitly as a "known risk" in the code's own docstring (`conftest.py`).

16. **`HTTPBearer` over `OAuth2PasswordBearer` for `get_current_user`** (Task 3A). `/auth/login` accepts a JSON body, not the OAuth2 password-flow's form-encoded `username`/`password` contract — `OAuth2PasswordBearer` would misrepresent that in the generated Swagger docs. Trade-off accepted: Swagger's "Authorize" dialog needs a token pasted in manually rather than offering a friendlier login form.

17. **Document Management (Task 3B) omits a `status` column**, deviating from the original Phase 1 design doc's `documents` schema sketch. That sketch anticipated the async parse→embed pipeline; Task 3B is explicitly upload/store/list/view/delete only (no parsing), so upload is synchronous and a status column would always read "ready." Revisit when a processing task actually needs it.

18. **`python-magic` deferred for Task 3B** — extension + declared Content-Type validation only for now. Deep content-byte sniffing (real production-standard practice, but requires the system `libmagic` library and a Dockerfile change) is deliberately pushed to the Phase 12 security-hardening pass rather than added speculatively now.

## 20. PROJECT MEMORY

*(Everything else worth knowing — assumptions, prior discussions, rejected ideas, philosophy — that doesn't fit cleanly into a numbered section above but matters for continuity.)*

**Origin and philosophy.** This project began as a brainstorm in `Project_Idea.ipynb` — an unstructured, enthusiastic 17-feature pitch explicitly framed around resume/interview value ("Recruiters LOVE this," "Huge interview point," difficulty rated "9–9.5/10... because you're integrating many components into one polished application"). The very first structured response to that pitch (captured as the "Phase 0 Planning" doc) deliberately pushed back on parts of the original enthusiasm — most notably talking the scope down from "Postgres + Qdrant + Redis from day one" to "pgvector only, Qdrant later," and from "GROBID from the start" to "PyMuPDF now, GROBID in Phase 3." **This push-the-scope-down instinct is a core, intentional pattern of this project and should continue** — the explicit stated principle is "one MVP, deployed early, extended incrementally," and "every extra moving part... gets introduced in the phase where it earns its keep," not speculatively. **Task 3B's dropped `status` column and deferred `python-magic` are the most recent examples of this same instinct.**

**The "resume evolution" framing is load-bearing for scope decisions, not just marketing.** The original notebook explicitly plans out how the resume bullet for this project should read differently at Month 1 vs Month 2 vs Month 3 — "it's still one project, but it keeps getting stronger." This means: it is more valuable for Phase 1 to actually ship (be deployed, be demoable) in a smaller/simpler form than to be more feature-complete but not deployed. **Deployment being the Phase 1 exit criterion is not a formality — it's the point.** Nothing is deployed yet; this should be treated as urgent once the core document/chat loop works, even ahead of polish.

**The "no code in this document" convention.** Both the Phase 0 and Phase 1 design docs explicitly state they contain zero code — they're implementation-ready specs, and actual code is written from them as a separate step. If the next Claude is asked to produce another planning/design document before code (e.g. for a "Phase 2 design doc"), that's consistent with the project's established workflow, not a deviation from it.

**Every completed task has been *manually or programmatically verified against real infrastructure*, not just written and assumed correct.** This shows up repeatedly: the DB migration was verified against a real (non-Docker) local Postgres 16 instance; the frontend auth flow was verified with an actual Playwright-driven Chromium browser; two real bugs were caught this way in Task 2.2 (cross-event-loop test engine, multi-byte-password bcrypt limit); and **Task 3A's `get_current_user` was verified not just via pytest but by manually invoking it against the real dev database with a real token, and by confirming a non-existent route returns 404 rather than 401** (proof the dependency has zero accidental footprint). **This verification discipline is a core project value and should be continued for Task 3B** — don't just write the document endpoints and their unit tests; actually exercise them with real files against a real running backend before considering it done.
